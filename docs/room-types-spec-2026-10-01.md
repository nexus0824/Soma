## 1단계: 레지스트리화 (동작 변경 없음)

목표: 새 방 유형 추가가 "데이터 + 핸들러 한 쌍" 으로 끝나게 한다. CLAUDE.md 의 "씬 코드에 분기를 늘리지 않는다" 원칙을 지킨다.

### 1-1. 방 유형 핸들러 레지스트리
- `Behaviors.js` / `Effects.js` 와 같은 패턴으로 `registerRoomType(id, handler)` 를 둔다. 파일 위치는 구현 세션이 기존 구조에 맞게 정한다(예: `combat` 이나 `ai` 와 같은 레벨의 새 모듈).
- 핸들러 인터페이스(초안)
  - `spawn(scene, room)`: 방 전용 스폰과 오브젝트 배치
  - `props`: 장식 프레임 설정(현재 `ROOM_PROPS` 값을 그대로 이관해도 된다)
  - `minimap`: 미니맵 표시 색
- `normal`, `spawn`, `exit` 는 `spawn` 핸들러가 없는 유형으로 둔다.
- `SceneGame.spawnRoomFeatures` 는 `room.type` 으로 핸들러를 찾아 호출하는 한 줄 루프로 줄인다.
- `treasure`, `elite` 를 핸들러로 이관한다. 중복된 팩 스폰 루프는 하나의 헬퍼로 합친다(예: 팩 크기, 엘리트 여부, 방 귀속).
- 일반 스폰 후보 필터(`type === 'normal'`)는 유형 핸들러가 "일반 몹 배치 가능 여부" 를 갖게 하거나 `normal` 만 허용하는 단일 지점으로 모은다.

### 1-2. 상호작용 대상 일반화
- `Chest` 를 일반 상호작용 객체의 한 구현으로 만든다. 공통점: 상태(`locked → active → used`), `canInteract(actor)`, `interact()`, 상호작용 안내 문구 키, `netState()`.
- `scene.chests` 와 `findInteractable` 을 `scene.interactables` 하나로 합친다.
- SceneUI 의 공격 버튼 "열기" 힌트(라벨, 키 안내, 색)가 `findInteractable` 결과의 안내 키를 읽도록 바꾼다. 샘은 "마시기" 같은 다른 문구가 필요하다.
- 미니맵이 상자 표시에 쓰는 정보도 상호작용 객체 단위로 읽게 한다.

### 1-3. 방 계획 확장 (데이터)
- `ROOM_PLAN` 항목에 `chance`(생략 시 1) 를 추가한다.
- 특수방 상한 규칙: 일반(normal) 방이 최소 3개 남도록 한다. 상한에 걸리면 이후 계획은 건너뛴다.
- 던전별 오버라이드가 필요하면 `Dungeons.js` 에 `roomPlan` 을 선택 필드로 둔다(없으면 기본값 사용).

### 1-4. 시드 결정성 (중요)
- 같은 시드는 같은 맵과 같은 스폰을 만들어야 한다(일일 던전, 멀티 대비).
- 기존 `treasure`, `elite` 의 배정 결과와 스폰 위치는 리팩터링 전후로 **동일**해야 한다.
- 새 확률 굴림(chance 등)이 기존 난수 순서를 흔들지 않도록, 기존 `rng` 와 `spawnRng` 가 아니라 별도 스트림(`floorRng(seed, floor, 'rooms')` 등)을 쓴다. 신규 계획 항목은 기존 항목 **뒤에** 추가해 기존 배정이 바뀌지 않게 한다.

### 1-5. 1단계 검증
- 리팩터링 전에 시드 5개 × 폐허 1~8층의 (방 유형 목록, 적 총수, 적 좌표 해시, 상자 좌표) 를 기록한다. 리팩터링 후 모두 일치해야 한다.
- 보물방 상자: 방의 적 전멸 후 활성화, E키와 모바일 공격 버튼으로 열기, 열면 골드 + 아이템이 나오는지 확인한다.
- 정예방: 무리 전멸 시 아이템 보상이 그대로 나오는지 확인한다.
- `npm run check` 통과.

## 2단계: 신규 유형 2종

### 2-1. 회복 샘 (`spring`)

| 항목 | 값(초기안) | 근거 |
|---|---|---|
| 계획 | `{ type: 'spring', count: 1, minRooms: 8, minFloor: 2, chance: 0.5 }` | 폐허(8방)에서도 나오게 하되 항상은 아니다 |
| 스폰 | 적 없음. 방 중앙에 샘 오브젝트 | 숨 돌리는 방 |
| 상호작용 | 즉시 활성, E키, 1회 사용 | 상자와 같은 조작 |
| 효과 | HP 40% + MP 50% 회복. 동료도 같은 비율 회복 | 회복약이 없는 현재 구조의 보완. 수치는 `Rooms.js` 상수로 둔다 |
| 사용 후 | 오브젝트가 비활성 상태로 바뀐다 | 반복 사용 방지 |
| 미니맵 | 녹색 표시 | 위치를 알 수 있어야 가치가 있다 |

- 스프라이트: 아틀라스(`assets/atlas/dungeon.json`)에서 샘 계열(`fountain`)이나 물약 계열(`flask`) 프레임을 먼저 찾는다. 없으면 `glow` 이미지 + 기존 프레임 틴트로 대체한다. 새 에셋 추가는 라이선스가 CC0 인 경우만 허용한다.

### 2-2. 미믹 상자 (`mimic`)

| 항목 | 값(초기안) | 근거 |
|---|---|---|
| 적용 | 보물방의 상자 중 일부(`chance 0.2`, `minFloor 3`) | 보물방의 단조로움을 깬다 |
| 겉모습 | 일반 상자와 동일. 가까이 가면 미세한 떨림(단서) | 공정성. 눈치 빠른 플레이어는 피할 수 있다 |
| 발동 | 상자를 열려는 순간 미믹 전투 시작(열기 입력 시) | 위험 vs 보상 |
| 적 정의 | `Enemies.js` 에 `mimic` 추가. HP 오우거급, 근접 공격, 짧은 돌진 1개 | 기존 `registerAbility`(charge) 재사용 |
| 보상 | 처치 시 일반 상자 보상 + 골드 ×1.5 + 희귀도 보정 +4 | 위험 감수의 대가 |
| 스프라이트 | 아틀라스의 `chest_mimic_open_anim` | 이미 있음 |

- 미믹 여부는 방 배정 단계의 별도 스트림에서 결정해 시드로 고정한다.
- 미믹 적 사망 시 보상 처리는 정예 보상(`remainingInRoom`)과 겹치지 않게 한다.

### 2-3. 공통
- 문자열은 `ko.js`, `en.js` 양쪽에 추가: 샘 사용 안내, 샘 사용 완료, 미믹 등장 로그, 상호작용 안내(마시기).
- 방 유형 이름이나 미니맵 범례를 표시한다면 그 문자열도 동일하다.
- 주석은 쓰지 않는다. 코드에서 이유를 알 수 없는 제약이 생기면 문구 후보를 제시해 사용자 확인을 받는다.
- 수치는 `Rooms.js`(방 상수) 와 `Balance.js`(난이도 수치) 에만 둔다.

### 2-4. 2단계 검증
- 시드 5개 × 폐허 2~8층에서 샘이 약 절반의 층에 나오는지, 미믹이 3층 이후에만 나오는지 확인한다.
- 샘: HP/MP/동료 회복량이 상수대로인지, 1회만 쓸 수 있는지, 미니맵에 표시되는지 확인한다.
- 미믹: 떨림 단서가 보이는지, 열 때 전투가 시작되는지, 처치 후 보상이 나오는지 확인한다.
- 일반 몹 밀집도: 폐허 8방 층에서 특수방이 늘어난 뒤 normal 방 1개당 평균 적 수가 얼마인지 **리팩터링 전후로 보고**한다. 3개 방에 20~36마리가 몰리면 과밀이므로 샘 확률 또는 상한을 조정한다.

## 확인 요청 (비차단)
- `SceneGame.openChest` 의 두 번째 아이템(SceneGame.js:284)은 희귀도 인자가 `undefined` 라 일반 등급도 나올 수 있다. 의도대로인지 확인해 주세요. 의도라면 두 번째 아이템의 최소 희귀도를 명시하는 방안도 검토해 주세요.
- 층 진행 상태(샘 사용 여부, 상자 개봉 여부)는 저장되지 않는다. 이어하기에서 샘을 다시 쓸 수 있는 문제는 이번 범위에 포함하지 않고, 별도 과제로 남긴다.
